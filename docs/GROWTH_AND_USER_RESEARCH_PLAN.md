# ForgeKit 第二阶段：推广、搜索需求与用户研究计划

> 制定日期：2026-07-30
> 执行周期：首轮 30 天
> 当前产品版本：v0.2.2-rc.1
> 核心原则：推广不是先追求曝光量，而是把对的人带到一个可验证的真实任务中。

## 1. 阶段判断

ForgeKit 已完成第一阶段的“可展示、可接入、可研究”基础：

- 官网与用户研究页面已上线；
- GitHub 问卷、试点反馈模板和访谈提纲已具备；
- Docker 构建诊断、Preflight、构建验证与 MCP 接入已有可运行实现；
- HarmonyOS 打包存在一个云手机样本，但正式签名与 AppGallery 上传尚未验证。

第一阶段尚不能记为“完成全面推广或市场验证”：

- 已联系 3 个公开候选；
- 已核验独立受访者 0 人；
- 已完成访谈 0 人；
- 已完成真实试用 0 次；
- 现有 5 条问卷回答来自同一 GitHub 账号，只能作为场景线索。

因此第二阶段的主任务不是继续横向加功能，而是完成下面这个闭环：

```text
搜索/社区触达
  → 进入对应问题页面
  → 提交真实失败或参与访谈
  → 完成一次计时试用
  → 给用户和需求打标签
  → 决定继续、收缩或扩展
```

## 2. 统一产品表达

### 2.1 当前主定位

一句话：

> ForgeKit 是面向初学者和 AI Agent 的 Docker 构建诊断与验证助手：构建前发现问题，失败后解释原因，成功后验证镜像确实能运行。

不要把下列表述作为当前主宣传：

- 万能打包平台；
- 一键上架所有应用市场；
- Agent 自动完成全部发布；
- 支持任意语言、任意系统、任意产物。

### 2.2 用户为什么需要它

用户不是因为需要“一个新系统”而来，而是因为现有工具链在任务交接处留下了判断缺口：

| 真实任务 | 现有缺口 | ForgeKit 当前价值 |
|---|---|---|
| 把项目交给别人运行 | 不知道入口、依赖和交付方式 | 识别项目并给出可审查计划 |
| Docker 构建失败 | 日志很长，不知道应改哪里 | 提取证据、分类原因、给出验证步骤 |
| AI 声称构建成功 | 只看到一句成功，无法确认 | 检查镜像、运行状态和产物证据 |
| Agent 调用本地构建工具 | 写操作边界与上下文不清楚 | 用 MCP 提供结构化、受约束的工具接口 |
| 需要发布移动应用 | 打包、签名、合规、上架混在一起 | 先检查产物和发布准备度，不代替账号与人工审核 |

## 3. 首批用户分层与标签

标签用于研究与产品决策，不用于给人贴固定身份。一个参与者可以同时具有多个标签。

### 3.1 用户标签

| 维度 | 建议标签 | 说明 |
|---|---|---|
| 角色 | `learner`、`indie_dev`、`maintainer`、`teacher`、`club_team`、`small_team_dev` | 谁在完成任务 |
| 项目 | `python_service`、`node_service`、`go_service`、`mcp_server`、`agent_app`、`harmony_app` | 正在交付什么 |
| 熟练度 | `first_docker_build`、`docker_user`、`release_owner` | 不使用模糊的“初级/高级”自评 |
| 触发事件 | `build_failed_now`、`handoff_needed`、`mcp_setup_failed`、`release_preparing` | 为什么此刻找工具 |
| 当前方案 | `raw_logs`、`search_engine`、`ask_ai`、`ci_logs`、`manual_checklist`、`other_tool` | 竞品是用户当前行为，不只是一款软件 |
| 主要障碍 | `environment`、`path_copy`、`dockerfile`、`dependency`、`registry_network`、`permission`、`disk`、`architecture`、`signing`、`compliance` | 与诊断语料类别尽量统一 |
| 结果 | `resolved`、`partially_resolved`、`unresolved`、`not_applicable` | 试用是否完成任务 |
| 复用信号 | `would_reuse`、`reused`、`would_not_reuse` | “愿意试试”不等于复用 |

### 3.2 需求标签

每一条需求必须记录：

```text
需求 ID
用户/场景标签
过去发生的真实任务
触发频率
失败成本
现有替代方案
可核验证据
请求的结果，而不是用户口述的功能
是否完成试用
是否第二次使用
```

证据等级从高到低：

1. `E4_reuse`：同一用户第二次真实使用；
2. `E3_pilot`：用自己的项目完成任务并记录前后结果；
3. `E2_behavior`：提供可核验的过去行为、日志或 Issue；
4. `E1_intent`：表示愿意试用或希望有某功能；
5. `E0_assumption`：团队内部判断或搜索词假设。

只有 E3/E4 才能直接推动重大功能进入承诺版本。E1/E2 用于决定下一轮该测试什么。

## 4. 搜索需求与术语体系

### 4.1 术语规范

| 对外中文 | 对外英文 | 使用边界 |
|---|---|---|
| Docker 构建诊断 | Docker build diagnostics | 当前主品类词 |
| 构建前检查 | preflight check | 构建前的环境和项目条件检查 |
| 构建失败解释 | build failure explanation | 面向初学者的结果表达 |
| 镜像运行验证 | container image runtime verification | 证明镜像存在且能够启动 |
| MCP 构建工具 | MCP build tool / MCP server for build diagnostics | 集成入口，不作为唯一价值主张 |
| 可审查构建计划 | reviewable build plan | `Forge.md` 的用户价值表达 |
| 发布清单 | release checklist | 不等于自动发布 |
| 发布准备度检查 | release readiness check | 检查签名、材料与产物状态，不执行上架 |
| 应用商店上架 | app store submission | 涉及外部账号、合规与审核，当前不自动执行 |

避免混用：`打包`、`构建`、`发布`、`上架`不是同一件事。

```text
构建：从源码产生镜像或安装包
打包：形成可分发产物
签名：用开发者身份为产物签名
发布：把产物交付到 Registry、Release 或其他渠道
上架：向应用市场提交材料并通过审核
```

### 4.2 搜索意图簇

以下是首轮待验证关键词，不预先声称有搜索量。每个词都应绑定一个页面、一个动作和一个衡量指标。

| 意图簇 | 搜索表达示例 | 用户想完成的任务 | 对应页面/CTA |
|---|---|---|---|
| 紧急排错 | `docker build failed`、`Docker 构建失败怎么办`、`failed to solve Dockerfile` | 快速知道错误原因 | 诊断示例页 → 提交脱敏日志 |
| COPY/路径 | `docker COPY failed file not found`、`failed to compute cache key` | 修复上下文或路径问题 | COPY 专题页 → 查看验证步骤 |
| 依赖失败 | `npm install failed in docker`、`pip install docker build failed` | 区分依赖、网络或版本问题 | 依赖专题页 → 运行诊断 |
| 环境检查 | `check before docker build`、`Docker 构建前检查` | 在构建前发现 Docker/磁盘/网络问题 | Preflight 页 → 复制 MCP 指令 |
| AI/MCP 集成 | `Docker MCP server`、`MCP build tool`、`Codex Docker build` | 让 Agent 安全调用构建能力 | MCP 配置页 → 10 分钟接入 |
| 项目交付 | `如何把 Python 项目打包给别人`、`Node project Dockerize` | 把服务交给别人运行 | 语言场景页 → 使用样例项目 |
| 可验证发布 | `verify docker image works`、`AI build verification` | 不相信“构建成功”的口头结果 | 验证页 → 查看 Manifest |
| 鸿蒙发布 | `HarmonyOS app 打包`、`HAP APP 区别`、`AppGallery 上架流程` | 理清构建、签名和上架步骤 | HarmonyOS 实验页 → 准备度清单 |

### 4.3 首轮页面优先级

先做 5 个高意图页面，不先建泛泛的博客：

1. `/docker-build-failed/`：失败诊断总入口；
2. `/docker-copy-failed/`：COPY、上下文、缓存键专题；
3. `/mcp-docker-build/`：Codex/Claude/Cursor/Cline 的 MCP 接入；
4. `/docker-preflight-check/`：构建前检查；
5. `/harmonyos-release-readiness/`：明确实验性，只讲 HAP/APP、签名与上架准备。

每页固定包含：真实错误片段、原因分类、不能确定的边界、验证动作、可复制的 ForgeKit 指令、访谈/试点入口。禁止为了 SEO 生成没有实测内容的批量页面。

## 5. 推广渠道与内容

### 5.1 渠道顺序

| 优先级 | 渠道 | 做法 | 成功指标 |
|---|---|---|---|
| P0 | GitHub Issues/Discussions | 只联系最近发生相关失败的项目；先帮助定位，再邀请试用 | 10 个有效对话、5 个试用 |
| P0 | 社团、课程、开源项目群 | 组织 30 分钟“带一个失败日志来”诊断活动 | 3 场、每场至少 2 个真实任务 |
| P1 | GitHub README/Pages | 用问题页承接长尾搜索，所有 CTA 指向真实任务 | 页面→试用转化率 |
| P1 | 掘金、知乎、CSDN、公众号 | 发布带可复现样本的诊断复盘，不发纯项目介绍 | 合格访问与日志提交数 |
| P1 | Reddit/Dev.to/Hacker News 相关讨论 | 英文发布技术案例；遵守社区规则，不群发 | 有上下文的评论与试用 |
| P2 | 短视频/直播 | 演示“原始日志 vs ForgeKit”计时对照 | 完整观看与试用，不看播放量单项 |

### 5.2 首批内容题目

- Docker 报错 `failed to compute cache key`，真正应该检查哪三处？
- 为什么 AI 说 Docker 镜像构建成功还不够？
- Codex/Claude 如何通过 MCP 做只读 Docker 构建诊断？
- npm/pip 在 Docker 里失败：依赖错误和网络错误怎么区分？
- HAP、APP、正式签名和 AppGallery 上架到底是什么关系？

每篇内容必须提供可复现输入、预期输出、验证步骤和当前局限。

### 5.3 推广纪律

- 不在无关 Issue 下发广告；
- 不把 Star、访问量或问卷意向当作需求成立；
- 不声称支持尚未验证的平台；
- 不收集密钥、私有源码、生产日志或不必要的私人联系方式；
- 同一用户的多个回答不能算多个独立参与者；
- 每个渠道使用独立 `utm_source`、`utm_medium`、`utm_campaign`，但不做默认个人追踪。

## 6. 用户研究执行方案

### 6.1 招募配额

首轮至少 12 名可区分参与者，确保不是只听一种声音：

| 分组 | 配额 | 必须满足 |
|---|---:|---|
| 最近 30 天 Docker 构建失败的开发者 | 5 | 有可描述的真实失败 |
| 第一次或较少使用 Docker 的学生/初学者 | 3 | 能观察安装与理解成本 |
| MCP/Agent 项目维护者 | 2 | 有真实交付或配置任务 |
| 教师/社团/小团队发布负责人 | 2 | 有重复教学或交接任务 |

HarmonyOS/AppGallery 作为额外探索样本，目标 3 个真实项目；不占 Docker 主线配额。

### 6.2 访谈只问过去行为

核心问题：

1. 最近一次把项目交给别人运行是什么时候？请从开始到结果讲一遍。
2. 最近一次 Docker 构建失败的原始错误是什么？你先做了什么？
3. 搜索过哪些词、看过哪些页面、问过谁？
4. 最后如何判断问题真的修好了？总共花了多久？
5. 哪一步必须靠你的经验判断，无法直接交给工具？
6. 如果现在重做一次，你会继续用当前方案吗？为什么？

产品演示放在访谈后半段。不要先问“你想不想要一键打包/上架”，因为这会制造礼貌性肯定。

### 6.3 试用测量

每次真实试用记录：

- 完成安装的时间、失败次数、人工帮助次数；
- 不使用 ForgeKit 时定位错误的基线时间；
- 使用 ForgeKit 后的定位时间；
- 分类是否正确、建议是否采用、验证是否通过；
- 用户是否理解为什么这样修；
- 7 天内是否第二次使用；
- 未完成时卡在哪一步。

## 7. 应用市场上架能力决策

### 7.1 当前决策

当前不做“自动上架华为及各大应用市场”。保留 HarmonyOS 实验适配器，新增能力若实施，应限制为：

1. 检查 HAP/APP 产物类型与构建模式；
2. 检查 bundleName、版本号与签名配置是否齐全；
3. 生成隐私政策、权限说明、截图、分级等发布材料清单；
4. 根据状态告诉用户下一步去 AppGallery Connect 做什么；
5. 输出机器可读的 `release_readiness`，但不登录账号、不上传、不提交审核。

### 7.2 为什么不直接自动上架

- 需要实名认证的开发者账号和主体责任；
- 正式证书、Profile 和密钥具有高安全风险；
- 隐私、权限、内容分级和素材必须由发布者确认；
- 商店政策变化快，且审核是人工/平台外部状态；
- 各市场接口和要求不同，会迅速把当前产品拖成高维护的发布平台。

### 7.3 进入自动化候选的门禁

某一应用市场只有同时满足以下条件才进入设计：

- 至少 5 个不同真实项目提出同类需求；
- 至少 2 名用户愿意用自己的开发者账号参加受控试点；
- 其中至少 3 个需求达到 E3 证据；
- 有可自动执行的构建、签名与安装验收环境；
- 凭证可以保留在用户/CI 环境，ForgeKit 不托管密钥；
- 能清楚区分“生成产物”“准备材料”“用户确认”“提交审核”四个状态。

即使达标，第一版也应是“生成提交包 + 用户确认”，不是无人值守发布。

## 8. 30 天执行排期

### 第 1 周：修正承接面并启动招募

- 统一官网、README、npm 描述中的当前版本、工具数量和定位；
- 增加 canonical、Open Graph、结构化数据、`robots.txt` 和 `sitemap.xml`；
- 发布前两个高意图问题页；
- 定向联系 10 个有近期真实失败的候选；
- 完成 3 次访谈和 2 次计时试用。

### 第 2 周：扩大真实任务样本

- 发布 COPY/路径与 npm/pip 两个案例；
- 举办第一次公开诊断活动；
- 累计完成 6 次访谈、5 次试用；
- 按本文标签整理需求，不按“想要的功能数”投票。

### 第 3 周：验证复用与相邻需求

- 追踪首批用户 7 天复用；
- 追加 MCP 配置与 Preflight 页面；
- 招募 3 个 HarmonyOS 发布准备探索样本；
- 只做发布准备度原型，不接真实商店上传。

### 第 4 周：作路线决策

- 汇总来源→试用→完成→复用漏斗；
- 对比各用户分组的安装时间、诊断时间和理解程度；
- 形成继续诊断、收缩解释层、强化 MCP 接入或探索发布准备的单一路线；
- 未达到门槛时不以新增平台替代用户验证。

## 9. 30 天目标与决策门槛

| 指标 | 30 天目标 | 解释 |
|---|---:|---|
| 合格访谈 | 12 | 有可核验的过去行为，不是泛泛意见 |
| Docker 真实试用 | 5 | 使用参与者自己的公开或脱敏项目 |
| 10 分钟内完成接入 | ≥80% | 记录人工帮助 |
| 定位时间缩短 | ≥60% 参与者 | 对比原方案基线 |
| 分类与建议可操作 | ≥80% | 由真实结果验证 |
| 7 天内第二次使用 | ≥2 人 | 核心复用信号 |
| 高意图页面 | 5 页 | 每页有真实样本和单一 CTA |
| HarmonyOS 探索项目 | 3 | 只评估准备度需求，不承诺上架 |

路线判断：

- 达到诊断门槛：继续扩充失败语料、语言项目和 CI 集成；
- 只需要日志解释：收缩为 Dockerfile/BuildKit Doctor；
- 主要卡在 MCP 配置：优先强化安装与配置诊断；
- HarmonyOS 准备度出现 3 个 E3 样本：设计独立的实验性 `release_readiness`；
- 没有 5 个真实 Docker 试用或没有复用：冻结横向功能扩张，保留教学与开源成果。

## 11. P2/P3 可持续收入实验

开源核心继续使用 MIT License。首轮不建立 SaaS 账户或云构建平台，先验证用户是否愿意为结果负责的服务付费：

| 实验 | 交付结果 | 首轮价格假设 | 成立证据 |
|---|---|---:|---|
| 单项目交付诊断 | 公开/脱敏项目构建、运行、健康验证与报告 | 99–299 元 | 至少 3 个独立预算信号，1 个真实付款 |
| 复杂项目交付跑通 | 定位失败、修复建议、可复核 Release Manifest | 300–999 元 | 至少 2 个 E3 试点，1 个真实付款 |
| 团队/课程导入 | 90 分钟工作坊、样例和交付检查流程 | 1000 元起 | 组织负责人确认预算并完成一场 |

收入漏斗必须分开记录：`paid-pilot-interest` 只代表预算意向，`paid-pilot` 必须有真实交易和已交付结果。不开虚假原价、不制造限时稀缺、不托管生产密钥。公开 Issue 不收集私人联系方式；实际签约和付款需由项目主体使用合规渠道处理。

30 天内若没有真实试用和复用，不用降价或扩平台掩盖问题；应先修复安装与价值交付。若有复用但无付费，继续保持开源工具并测试培训/导入服务，而不是把已有核心突然收费。
