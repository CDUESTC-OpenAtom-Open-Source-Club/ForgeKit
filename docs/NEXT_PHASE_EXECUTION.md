# 下一阶段执行方案

> 状态日期：2026-08-07
> 阶段名称：真实试点与精准获客
> 阶段目标：证明真实用户愿意用 ForgeKit 解决 Docker 构建失败，并在新的失败中再次使用。

## 1. 阶段结论

ForgeKit 可以开始下一阶段，但当前阶段不是大规模发布，也不是继续扩展平台数量。下一阶段只做两件事：

1. 用真实用户验证 Docker 失败诊断是否节省时间；
2. 把已有真实失败转化为可搜索、可复制的诊断入口。

内部的 MCP、`Forge.md`、Preflight、构建和运行验证继续保留。对外首屏只强调两个入口：

```text
已有失败日志 → forgekit diagnose
完整项目交付 → forgekit deliver
```

## 2. 用户优先级

首批只招募最近 30 天内发生过以下事件的人：

| 优先级 | 用户 | 触发事件 | 目标结果 |
|---|---|---|---|
| P0 | 独立开发者、学生开发者 | Docker 构建失败且看不懂日志 | 找到原因并完成验证 |
| P0 | MCP Server/Agent 项目维护者 | 镜像能构建但无法启动或运行 | 得到运行验证证据 |
| P1 | 小团队开发者 | 需要把服务交给他人运行 | 生成可复用镜像和结果清单 |
| P1 | 教师、开源社团 | 需要演示从代码到镜像 | 复现同一个失败与修复过程 |

暂不以移动应用、企业治理或通用 MCP 配置管理作为获客主线。

## 3. 30 天试点计划

| 周期 | 工作 | 验收证据 |
|---|---|---|
| 第 1 周 | 完成公开接入路径、诊断入口和 3 个案例页 | 干净环境可运行；安装文档只有一个 commit |
| 第 2 周 | 定向联系 10 个近期有公开 Docker 失败的项目 | 至少 3 个有效回复 |
| 第 3 周 | 完成 5 次真实计时试用 | 记录基线时间、ForgeKit 时间、人工帮助和最终结果 |
| 第 4 周 | 追踪二次使用并发布脱敏案例 | 至少 2 次二次使用，形成继续/收缩决策 |

每次试点必须使用用户自己的公开或脱敏项目，不能用仓库 fixture 代替真实激活。

## 4. 获客方式

优先发布“问题解决内容”，不发布泛泛的产品介绍：

- `docker build failed`：解释错误证据和最小验证步骤；
- `failed to solve`：按 COPY、依赖、网络、权限和架构分类；
- `COPY failed`：展示 build context 与 `.dockerignore` 的真实案例；
- `npm install` / `pip install`：展示容器内依赖环境的对照检查；
- `container starts but healthcheck fails`：展示构建成功不等于服务可用。

每个页面必须有一个直接动作：复制 `forgekit diagnose` 命令，或提交一次真实试点。不要把 Star、clone 或页面访问当作激活。

## 5. 继续开发的门槛

只有达到以下结果，才进入 Node/Go 扩展、CI 集成或 arm64 正式支持：

- 至少 5 名可区分的非维护者完成真实试用；
- 80% 用户能在 10 分钟内完成接入；
- 至少 60% 用户的定位时间缩短；
- 失败分类和建议覆盖率达到 80%；
- 至少 2 名用户在 7 天内再次使用；
- 没有日志泄露、危险默认命令或不可解释的高置信度误判。

如果用户只持续使用日志诊断，则把产品收敛为 Docker/BuildKit Doctor；如果用户持续需要交付验证，再保留 `deliver` 和 `Forge.md` 作为第二条路径。

## 6. 禁止提前做的事

- 不因为流量低就增加平台数量；
- 不把问卷意向计为用户需求；
- 不把 GitHub clone 计为真实用户；
- 不默认上传源码、日志或环境变量；
- 不在 npm 正式入口、独立样本标注和真实试点完成前做大规模宣传。
