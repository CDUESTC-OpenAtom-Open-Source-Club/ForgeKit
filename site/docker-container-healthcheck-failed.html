container starts but unhealthy

容器起来了，但接口没反应——构建成功不等于服务可用。

`docker build` 成功只代表镜像能形成。进程是否保持运行、端口是否真的在监听、健康路径是否可达，是另一组验证。健康检查失败时先分清是入口迁移、端口、路径、权限还是监听地址。

先纠正假设

四条独立证据，缺一条都不能说“能跑”。

  1. 1

    容器保持运行

    `docker ps` 不带 `-a` 时能看到它，且没有被退出码标记。

  2. 2

    端口被监听

    容器内进程实际绑定到你映射的主机端口，而不是只在容器内随机端口。

  3. 3

    健康路径可达

    你请求的 health 路径存在且返回预期状态码。

  4. 4

    数据库 / 依赖就绪

    服务依赖的库、网络或外部依赖真正可用，而不是启动即重试。

五处检查

健康检查失败，按顺序排除入口、端口、路径、权限和监听。

入口

CMD/ENTRYPOINT 是否真的存在

镜像里有文件，但 CMD 指向路径缺失或命令不存在。核对 Dockerfile 的 CMD / ENTRYPOINT 与项目真实入口。

端口

映射或监听地址

应用可能只监听 `127.0.0.1`，导致容器外部访问不到。确认 `EXPOSE`、`-p` 映射与进程实际绑定地址。

路径

健康端点

请求 `/health` 之前，先用 `docker exec` 在容器内 `curl -i` 同一个地址，判断是路径不对还是整个服务没起。

权限

运行用户对目录可写

以非 root USER 运行时，数据目录可能不可写导致启动后退出或进入重试。

依赖

外部服务就绪

数据库或 Registry 未就绪时，进程可能无限重试。先确认依赖可用，再判断是否健康。

两条验证命令

先在容器内看真实状态，再查主机侧。

容器内最小验证
# 确认进程与监听地址
docker exec <容器> sh -c "ps; netstat -ltn" 

# 在容器内直接请求健康端点，排除主机映射问题
docker exec <容器> curl -i http://127.0.0.1:<端口>/health
