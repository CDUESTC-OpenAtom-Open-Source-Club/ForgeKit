免费、开源、先解决真实构建失败

Docker 构建失败，不该只留下一整屏日志。

ForgeKit 不替代 Docker。它帮助 Agent 在构建前发现问题，在失败后解释原因，并验证最终镜像真的能够运行。

先解决最常见的问题

初学者真正卡住的，常常是看不懂构建为什么失败。

ForgeKit 当前不追求覆盖所有平台，先把 Docker 构建问题检查清楚、解释清楚、验证清楚。

问题 1

“这个项目该怎么给别人运行？”

ForgeKit 先识别项目，再给出适合当前范围的交付建议，不要求你先成为发布工程师。

问题 2

“构建失败后，我该改哪里？”

错误被整理成原因、日志和建议动作，而不是把一整屏命令输出直接扔给你。

问题 3

“AI 说成功，我怎么相信？”

交付结果会关联 Git 提交、构建环境、镜像与校验值，让成功可以被再次检查。

从一次失败开始

先诊断已有日志，再决定是否接入完整交付。

第一入口不需要 MCP，也不上传源码：把一次脱敏后的 Docker/BuildKit 日志交给本地 CLI。

1

保留失败日志

从本地 Docker 或 CI 构建中保留必要上下文，先移除密钥、Token 和私人路径。

2

运行只读诊断

Node.js 18+ 即可开始，不需要先配置 MCP，也不会修改项目。

3

验证下一步

查看错误类别、证据、建议动作和确认修复所需的验证步骤。

本地只读诊断
npx --yes --package=github:CDUESTC-OpenAtom-Open-Source-Club/ForgeKit#88c945a \
  forgekit diagnose ./docker-build.log

已识别诊断退出 0，未知诊断退出 1，输入错误退出 2。确认问题后，再用 完整交付流程 构建并验证镜像。

七个工具，一个可审查流程

每一步只做一件事，也明确告诉你下一步。

  1. 01
    inspect_project

    先认识项目

    识别语言、入口和已有构建配置。

  2. 02
    generate_packaging_plan

    生成可审查计划

    把目标、决策与风险写进 Forge.md。

  3. 03
    preflight_check

    提前发现问题

    检查目录、计划、运行时、磁盘与 Registry。

  4. 04
    diagnose_build_failure

    解释已有构建失败

    只读分析脱敏日志，返回证据、原因、置信度和验证步骤。

  5. 05
    build_docker_image

    构建并验证镜像

    只有计划存在时才执行，并记录结果证据。

  6. 06
    pack_deb

    按需生成 deb

    仅适合明确的 Ubuntu/systemd 场景。

  7. 07
    pack_harmonyos_app

    实验性 HarmonyOS 打包

    已有 HAP 云设备样本；正式签名与 AppGallery 提交仍未验证。

清楚说明边界

我们宁愿少承诺，也不让初学者被错误信息误导。

Alpha 当前适合

  • 学习 AI Agent 的规范交付流程
  • Python、Node.js/TypeScript、Go 服务项目试点
  • 本地 linux/amd64 OCI/Docker 镜像
  • 构建前检查、错误解释与结果追溯

当前不承诺

  • 任意项目一键自动发布
  • 企业生产环境或合规认证
  • 自动修改镜像源、系统服务或防火墙
  • Windows、macOS、Android、iOS 全平台支持

从具体失败开始搜索

每一种失败，都有对应的排查入口与可复制的诊断命令。

COPY failed · 找不到文件

构建上下文、相对路径与 .dockerignore

`file not found`、`failed to calculate checksum`、`failed to compute cache key` 往往不是 Docker 坏了。

看 COPY 排查 →
failed to solve · 总入口

先按 network / COPY / 依赖 / 权限 / 磁盘 / 架构分类

不要反复 --no-cache 重试，先看这一句下面是哪一类步骤失败。
