四类原因对症检查用命令定位全部诊断

dependency install

容器里的依赖装不上，问题常在“约束”而不在“缓存”。

`npm install` 和 `pip install` 在容器内失败，先分清是版本约束冲突、锁文件不同步、包或索引不存在，还是单纯网络不通。别一上来就清缓存、加 `--legacy-peer-deps` 或关校验。

分析一段失败日志查看接入文档
先分类

失败信息自己会说出是四种原因里的哪一种。

约束冲突

`ERESOLVE` / `resolutionimpossible`

依赖之间的版本要求无法同时满足。用 `npm explain <包>` 或多个依赖的冲突链定位，优先调整显式版本约束，而不是默认加宽松参数。

锁文件

`package-lock` 与 `package.json` 不同步

`npm ci` 只有在锁文件反映当前 package.json 时才工作。在受信任环境 `npm install` 更新锁文件，审查后提交。

包不存在

`could not find a version` / `unable to locate package`

包名、版本、Python/Node 版本、架构或索引源不兼容。核对包名和版本范围，并确认所使用的索引源。

网络

`network is unreachable` / 超时

DNS、代理或 Registry 连接失败。单独拉基础镜像或访问失败的依赖端点，确认连接与镜像源。

字面证据 vs 根因

打印的“找不到包”有时只是真因的最后一行。

  1. 1

    看 npm/pip 自己的报错

    是 `ERESOLVE`、`no matching distribution` 还是 `network is unreachable`？三者验证方式不同。

  2. 2

    在干净目录重建

    用锁文件跑 `npm ci` / 新虚拟环境 `pip install`，区分“项目状态”与“环境状态”。

  3. 3

    确认索引与网络

    `npm ping` / `python -m pip index versions <包>` 单独验证，再把结论应用到 Dockerfile。

本地只读诊断

一条命令把这几种失败分类成证据和下一步。

诊断命令
npx --yes \
  --package=github:CDUESTC-OpenAtom-Open-Source-Club/ForgeKit#88c945a \
  forgekit diagnose ./docker-build.log

需要 Node.js 18+；日志只在本机处理，不上传。退出 0 = 已识别，1 = 暂未知，2 = 输入错误。
