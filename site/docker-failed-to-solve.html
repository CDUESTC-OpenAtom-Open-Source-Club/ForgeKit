context 是谁按类别定位用命令定位全部诊断

failed to solve

`failed to solve` 不是根因，是“某个步骤失败”的总入口。

BuildKit 在 `STEP …: failed to solve` 之后通常会补一句具体原因。不要反复 `--no-cache` 重试，先看这一句下面是 network、COPY、Dockerfile、依赖、权限、磁盘还是架构。ForgeKit 只读诊断会把这一句整理成类别、证据、置信度和可验证的下一步。

分析一段失败日志COPY failed 单独看
先弄清楚 context

最后一行决定 Docker 能看到什么，也决定多数 failed 指向哪里。

命令与目录
# context 是命令末尾的 "."，不是 Dockerfile 所在目录
docker build -f docker/Dockerfile .

# 从 context 根目录引用文件
COPY package.json ./

只要失败步骤出现在 COPY / ADD 或 `npm install` / `RUN apt-get` 之前，优先怀疑 context 与路径；出现在依赖下载时，优先怀疑网络与 Registry。

按类别定位

同一句 total，不同的下一行，对应不同的检查。

网络 / Registry

下载或校验失败

`network is unreachable`、`dial tcp … i/o timeout`、`unauthorized …`。先单独拉一次基础镜像或失败的依赖端点，确认连接与凭据。

构建上下文 / COPY

文件不存在

`COPY failed`、`failed to calculate checksum`、`failed to compute cache key`。从 context 根目录检查路径、大小写与 `.dockerignore`。

Dockerfile

解析或语法

`Dockerfile parse error`、`unknown instruction`。按证据行号修正指令，不要整段重写。

依赖

npm / pip / apt

`ERESOLVE`、`resolutionimpossible`、`unable to locate package`。先在干净目录用锁文件重建，再检查索引源。

权限

拒绝访问

`permission denied`。确认路径所有者与 USER，避免递归放宽权限或无条件 sudo。

磁盘

空间不足

`no space left on device`。先 `df -h` 与 `docker system df`，再由用户决定清理什么。

架构

平台不匹配

`exec format error` 或 manifest 不匹配。核对 `--platform`、基础镜像与编译目标架构。

最小重试

一次只改一个变量，把剩下的失败样本保留下来。

  1. 1

    保留失败上下文

    复制失败步骤前后的日志，移除 Token、密钥与私人路径。

  2. 2

    判断类别

    先定位到某一个类别，再对症检查，而不是一上来清缓存。

  3. 3

    验证再重试

    只改一个变量，确认后重试；仍失败时保留样本。

本地只读诊断
npx --yes \
  --package=github:CDUESTC-OpenAtom-Open-Source-Club/ForgeKit#88c945a \
  forgekit diagnose ./docker-build.log

需要 Node.js 18+；日志只在本机处理。退出 0 = 已识别，1 = 暂未知，2 = 输入错误。
