Docker build diagnostics

Docker 构建失败，先找到证据，再决定改什么。

`docker build` 或 BuildKit 报错时，最后一行不一定是根因。ForgeKit 的只读诊断会保留脱敏证据，分类可能原因，并给出可以验证的下一步；不能确定时会返回 unknown，而不是编造修复。

分析脱敏日志提交真实案例
推荐顺序

不要一上来就重装 Docker 或放宽权限。

  1. 01

    保留最小错误上下文

    保留失败步骤前后的必要日志；先移除 Token、密钥、邮箱、用户名和私人路径。

  2. 02

    区分问题类别

    环境、构建上下文、Dockerfile、依赖、Registry/网络、权限、磁盘或架构，需要不同的验证方式。

  3. 03

    验证假设

    执行只读或低风险检查，确认建议是否适用。不要把 `sudo`、关闭校验或放宽权限当成默认答案。

  4. 04

    再运行最小重试

    只改变一个变量，记录是否解决；保留仍然失败的案例，因为 unknown 也是有价值的结果。

结构化结果

同一份日志，输出证据、原因和验证动作。

下面展示结果结构，不表示所有错误都能被自动修复。

1

category

把错误归入可验证的类别，而不是只复述日志。

2

evidence + confidence

保留判断依据，并明确置信度边界。

3

suggested_actions + verification

说明适用条件，并给出确认是否修复的步骤。

示例输出
{
  "category": "path_or_copy",
  "summary": "构建上下文中找不到 COPY 源文件",
  "confidence": "high",
  "evidence": ["COPY failed: file not found"],
  "suggested_actions": ["检查 build context 与 .dockerignore"],
  "verification": ["从实际 context 根目录确认文件可见"]
}
当前接入方式

npm 包尚未公开，使用已验证的 GitHub commit。

需要 Node.js 18+。首次运行会下载和 clean build；请勿提交私有源码、密钥或未经脱敏的生产日志。

临时直装
npx --yes --package=github:CDUESTC-OpenAtom-Open-Source-Club/ForgeKit#f5fbc4e forgekit-mcp
参加 15–20 分钟计时试用查看完整接入文档
